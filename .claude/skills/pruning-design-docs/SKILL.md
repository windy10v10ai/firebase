# 精简已完成的设计文档

## 核心原则

设计文档记录「为什么这样做」，不是「代码现在长什么样」。批次上线后，凡是打开对应源码就能看到的内容——组件清单、prop 名、文件路径、精确的样式类名——统统删除；只留读代码看不出来的部分：设计意图、权衡过程、拍板的决定、至今仍然生效的约束。

判断一句话该删还是该留，只问一个问题：**这句话在说「代码长什么样」，还是在说「为什么长这样」？** 前者删，后者留。

## 什么时候用

- 一个批次/阶段的设计文档（`docs/design/<主题>/<阶段>.md`）状态改成「已完成」「已上线」，准备合并 PR 之前
- 被要求审查某个主题下的设计文档，看有没有过时或冗余内容

**不适用**：文档还在「进行中」；或者是持续被后续批次引用的「活规范」，比如视觉风格 token 表——后面的批次还要照着做，不是历史记录，不能按「已完成」的标准瘦身。

## 删除清单

批次标记完成后，直接删除：

- **验收标准、测试清单**：只在开发期间有用，上线后查 PR 记录就够了。哪怕清单里有没打勾的项也一并删——那是给 PR 讨论的信号，不是文档该长期背着的内容。
- **组件/接口清单，如果只是在转述当前代码**：prop 名、文件路径、能直接打开源码看到的实现细节。自问这份清单是不是只在说「这里有个 XxxCard，负责渲染 yyy」而不解释为什么这么分——是，就删。
- **孤立的过程性描述**：「目前是这样，之后要改成」这类只叙述改动过程、改完即失去意义的句子。**例外**：如果「现状问题」紧接着就是由它推出的决定（问题 → 决定），问题本身是决定的理由，不删——删了后面的决定就变成没有来由的断言。

## 保留清单

- 一句话结论（做什么）
- 为什么这么设计、放弃了哪些方案、当时权衡了什么
- 明确「不做什么」及其原因
- 与仓库默认约定不一致的例外——注明「例外记录见 xxx.md」这样的指针，不重复抄一遍内容本身
- 至今仍然生效、后续批次要遵守的约束
- 尚未做的后续依赖/事项

## 常见错误

| 错误 | 应该怎么做 |
|---|---|
| 保留了已经在别处（如视觉风格文档）记录过的规则 | 换成一句「例外记录见 xxx.md」的指针，不重复内容本身 |
| 因为清单看起来「有用」就留着组件/接口清单 | 反问：这份清单只看代码能不能得到？能，就删 |
| 把还没打勾的测试项留着当提醒 | 提醒放 PR 讨论里，不进文档；文档不背验证状态 |
| 整篇只留一句结论，删光了取舍过程 | 决策的「为什么」要留，不是只留「是什么」 |

## 例子

批次完成前：

```markdown
## 页面与组件

- 会员页的平台标题继续使用品牌色，价格继续使用会员金色；仅两个 `PlatformCard` 订阅按钮使用 `.btn-season`。
- 商业披露标题使用 `--color-heading`，说明与更新时间使用正文和次要文字 token。
- `DataTable` 使用 `--color-panel` 与 `--color-panel-soft` 区分行层级；375 宽度渲染语义化卡片列表，768 与 1280 宽度渲染表格。
- `Section` 已提供当前页面所需的宽度能力，不增加新的 props。
```

精简后（第一条已在 phase-7 记录过，换成指针；第三条是本批次独有、代码里看不出「为什么」的决定，留；其余是纯实现细节或「没做什么」，删）：

```markdown
**会员页保留既有排版，订阅按钮统一使用紫色主按钮（例外记录见 phase-7-visual-style.md）。**

## DataTable

窄屏（<640px）渲染标签—内容卡片列表，768 及以上渲染表格；行层级用 `--color-panel` 与 `--color-panel-soft` 区分。
```
