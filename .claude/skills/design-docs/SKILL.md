# 设计文档的选址与瘦身

## 核心原则

设计文档记录「为什么这样做」；框架性文档记录「系统现在长什么样、为什么这么搭」；实施计划记录「打算怎么做」。三者生命周期不同，放错地方要么被遗忘要么被误当长期真相。

## 新文档放哪里

| 内容性质 | 放哪 | 进 git | 生命周期 |
|---|---|---|---|
| 某个模块长期有效的架构、鉴权、技术选型（不随单次批次增减） | `docs/<模块>/README.md`（如 `docs/web/README.md`，日后可有 `docs/api/README.md`） | 是 | 只在决策变更时更新，不因批次完成而删减 |
| 某个模块长期有效、内容多到放进 README 会喧宾夺主的专题规范（如网站的配色、按钮与可点击元素） | `docs/<模块>/<专题>.md`（如 `docs/web/design-system.md`），README 只留一句结论加链接 | 是 | 同上 |
| 某次批次/功能/迁移的具体设计（brainstorming 产出的 spec） | `docs/design/<主题>/<阶段>.md` | 是 | 批次完成后压成短文，见下 |
| 某次实现的任务拆解（writing-plans 产出的 plan） | `docs/superpowers/plans/YYYY-MM-DD-<名字>.md` | 否，`.gitignore` 已排除 | 随代码合入即失效，不需要留痕 |

`<主题>`：kebab-case，一个长期方向一个目录，如 `local-host`、`web`、`player-stats-recent`。`<阶段>`：该主题下的阶段或子步骤，如 `phase-1-backend.md`。

判断一份新文档该进哪一类，问：**这份内容会不会因为某次批次完成就失效？** 会失效 → `docs/design/`；不会、且描述的是系统现在的样子 → `docs/<模块>/`；只是任务清单、完成就扔 → `docs/superpowers/plans/`，不进 git。

**这个问题要逐段问，不是整份文档问一次。** 一份批次设计里常常混着两种内容：取舍过程（比较过哪些方案、为什么选这个）会失效，最终规范（token 取值、组件规格、选型规则表）不会。**规范本身必须写进 `docs/<模块>/`，批次文档只写取舍并链接过去**；批次文档会被压短甚至整篇删除，只存在于批次文档里的规范会跟着消失。只在 README 里留几句结论、把取值表和规格留在批次文档，不算同步完成。

## 文档里的图片

框架性文档的图画的是**规范本身**——以后做新页面时拿来对照的东西：色板、组件在各个状态下的样子与尺寸、通用的交互样式。做法：

1. 在设计稿里按最终取值画一张规范画板（一个主题一张，如色板、按钮状态矩阵、可点击元素）
2. 渲染成图片，裁掉空白，存 JPEG，单张 200 KB 以内
3. 放 `docs/<模块>/images/<专题>/`，由对应的规范小节引用

| 图 | 放不放 |
|---|---|
| 规范画板（色板、组件状态矩阵、交互样式） | 放在框架性文档 |
| 已实现页面的截图 | 不放：看页面本身即可，截图还会随页面改动过时 |
| 方案对比、改前改后、设计过程的画板 | 不放：留在设计稿与 PR |
| 完成后的批次文档里的任何图 | 不放 |

## 批次完成后的文档长这样

完成后的批次文档**一屏读完**（正文约 30 行以内），只由下面几部分组成，按这个顺序：

1. **状态行**：`> 状态：已完成。` 加长期规范所在的 `docs/<模块>/` 链接
2. **一句话背景**（可选）：要解决的问题，一两句
3. **决定**：列表，每条一句——粗体写决定，冒号后写为什么。没选的方案若值得一提，在理由里带半句「没选 X，因为 Y」
4. **不做**：列表，每条一句，带原因
5. **后续事项**（有才写）：还没做、依赖别处的事

除此之外的内容各有去处，不留在完成后的文档里：

| 内容 | 去处 |
|---|---|
| 取值、规格、选型规则表 | `docs/<模块>/`（完成前就该挪过去） |
| 方案比较表、未采用方案的细节、决策过程 | PR 与设计稿 |
| 验收标准、测试清单、截图 | PR |
| 改动前是什么样、组件与文件清单、实现细节 | git 历史与代码 |
| 已在别处写过的规则 | 一句「见 xxx.md」 |

**架构、鉴权等描述系统现状的内容不属于批次文档，发现了就挪进对应的 `docs/<模块>/`，不要压短时顺手删掉。**

## 常见错误

| 错误 | 应该怎么做 |
|---|---|
| 把架构、技术选型这类长期内容写进批次文档 | 挪进 `docs/<模块>/README.md`，批次文档只留指针 |
| README 里写了几句结论，token 取值、组件规格、选型表却留在批次文档 | 规范整体挪进 `docs/<模块>/<专题>.md`，批次文档只留取舍 |
| 完成后的文档仍保留方案比较表、各方案的利弊展开 | 每个决定一句理由，没选的方案最多半句 |
| 在框架性文档里贴已实现页面的截图，或提交方案对比、改前改后的过程图 | 换成按最终取值画的规范画板（色板、组件状态矩阵），过程图留在设计稿与 PR |
| 整篇只留一句结论，删光了理由 | 每个决定仍要一句「为什么」 |
| 把 writing-plans 产出的任务清单提交进 `docs/design/` | 实施计划不进 git，留在 `docs/superpowers/plans/`（已被 `.gitignore` 排除） |

## 例子

完成后的批次文档：

```markdown
# 批次 12：配色体系

> 状态：已完成。长期规范见 [docs/web/design-system.md](../../web/design-system.md)。

紫色曾同时是勇士积分色、全站交互色和默认按钮色，玩家分不清哪块紫在说积分、哪块在说「能点」。改成每种颜色只管一件事。

## 决定

- **网站主色用电光蓝**：中性白在深色页面里太抢眼，青、绿会分别挤掉每日任务色与「绿 = 成功」
- **每个功能一个图标色**：属性用勇士紫，觉醒参考游戏的 `#d000ff` 调成 `#dd53e7`，原色缩成图标后和勇士紫读成同一种紫
- **品牌色只上平台标识**，删掉赞助平台各自的渐变按钮：品牌色都和站内有含义的颜色同色系

## 不做

- 不改游戏按钮的取值
- 不引组件库
```
