# 每日挑战后端测试与验收

## 1. 验收边界

后端验收分为四层：

1. 类型、lint 和构建；
2. 单元测试与控制器测试；
3. 本地 Firestore/API 集成验证；
4. Dota 开局、结算、跨日和奖励展示联调。

前两层不能证明 Firestore 事务、真实积分账户、Dota 采集或游戏内 UI。上线结论必须同时记录后端证据和游戏端证据。

## 2. 环境门禁

所有 worktree 共用项目根目录的唯一 Firestore 数据和本地 API。不得在功能 worktree 内复制数据库或创建空库。

固定验收拓扑：

| 服务 | 地址 |
|---|---|
| Firestore Emulator | `127.0.0.1:8080` |
| NestJS API | `127.0.0.1:3001` |
| Dota 鉴权代理 | `127.0.0.1:5000` 转发到 `3001` |
| 测试 GUI | 通常为 `4000` |

固定验收玩家 SteamID：`483215844`。启动后必须实际读取该玩家赛季积分、会员积分、会员状态和属性数据，不能只检查端口。

本轮文档整理不得启动或停止上述共享服务；执行本手册时先确认没有其他任务正在使用。

## 3. 静态验证

在后端 worktree：

```powershell
Set-Location .\api
npm run lint
npm run build
npm test -- --runInBand
```

定向测试至少覆盖：

```powershell
npm test -- --runInBand daily-challenge
npm test -- --runInBand game.controller.daily-challenge
npm test -- --runInBand members.service.daily-boundary
```

若 Jest 的匹配方式因项目配置不同，以实际测试文件路径执行。记录命令、退出码、测试数量和失败名称。

仓库差异检查：

```powershell
git diff --check
```

## 4. 配置验收

对审核配置执行：

1. 保存草稿并确认请求成功。
2. 确认校验结果为 `0 errors / 0 warnings`。
3. 发布后读取 `published`。
4. 核对配置 ID、版本和 404 条任务。
5. 核对 19 条通用个人、381 条英雄专属、4 条共同任务。
6. 核对 127 名英雄每名 3 条专属任务。
7. 核对个人、共同、连续和刷新积分。
8. 核对全部纯粹伤害任务存在有效证据。
9. 核对规范化哈希与原始文件字节哈希所使用的口径。
10. 查询版本列表和审计记录。

回滚验收：发布第二个测试版本，回滚到前一版本，确认发布指针变化，而已存在挑战日的 `configVersionId` 不变化。

## 5. 玩家接口验收

### 5.1 快照

- 新挑战日首次请求创建玩家状态；
- 同一玩家重复请求返回同一组三候选；
- 候选为两条不同分类通用任务和一条英雄专属任务；
- `needsSelection = true`；
- `globalTask` 与同日其他玩家一致；
- 连续、刷新、未读数和最近奖励字段完整。

### 5.2 接取

- 接取候选成功并返回 `accepted`；
- `acceptedTask.assignmentId` 与请求一致；
- 再次使用同一 `requestId` 返回同一结果；
- 换一个 `requestId` 再次接取返回 `already_selected`；
- 非候选 assignment 返回 `invalid_candidate`；
- 关闭日返回 `day_closed`。

### 5.3 刷新

- 非会员返回 `not_member`；
- 会员第一次刷新费用为 `0`；
- 后续费用依次为 `10、20、30、50、50`；
- 余额不足返回 `insufficient_member_points`；
- 次数用完返回 `refresh_limit_reached`；
- 已接取后刷新返回 `already_selected`；
- 同一 `requestId` 重试不重复扣费；
- 候选更新与会员积分扣除必须同时成功或同时失败。

### 5.4 查看奖励

- 有未读奖励时 `unreadRewardCount` 正确；
- `/game/start` 领取后奖励为 `notified`；
- `view` 后变为 `viewed`；
- 同一 `requestId` 重试不重复修改或返回异常。

## 6. 比赛进度验收

构造固定 `matchId` 和 `matchStartedAt`，逐项验证：

- 个人指标与已接任务匹配时累计；
- 未接取时个人进度不增加；
- assignment 不匹配时个人进度不增加；
- 英雄专属任务英雄匹配时累计，不匹配时不累计；
- 个人进度在目标处封顶；
- 共同任务无需接取即可累计；
- 共同贡献保持真实总量，不按目标封顶；
- `normallySettled = false` 不落库；
- 不属于基础 `eligiblePlayers` 的玩家不落库；
- 断开玩家不落库；
- `dayId` 与 `matchStartedAt` 不一致时拒绝；
- 指标数据版本不足时拒绝该指标；
- 负数、非整数、未知指标和超过单局上限的数据被拒绝；
- 相同 `matchId + steamId` 重试不重复累计；
- 个人任务完成时，玩家状态、比赛 ledger、赛季积分和奖励 ledger 同事务提交；
- 奖励写入失败时，玩家进度、轮次和比赛 ledger 均不提交；
- 首次 `/game/end` 响应丢失后重试，会回显同一笔个人奖励供赛后展示，但不会重复增加积分。
- `/game/end` 在挑战进度提交成功后返回通过基础结算且未断开玩家的结算后 `dailyChallenges`；即使本局没有个人奖励，也能返回最新轮次与进度快照；
- 结算后快照读取失败时只省略 `dailyChallenges`，不阻断基础结算，也不撤销已提交的挑战进度；

19 种指标逐项覆盖，特别检查版本 2 指标：三种伤害类型、Bot、肉山以及七种控制/负面时长。

## 7. 跨日与宽限期验收

使用可控时间分别执行：

1. `endsAt` 前开始并在 `endsAt` 后回传：归属原挑战日。
2. `endsAt` 后开始：归属新挑战日。
3. 原挑战日处于 `closing` 且未到 `closesAt`：接受原日比赛回传。
4. 到 `closesAt` 后：冻结共同贡献。
5. 冻结后重复上传旧比赛：不改变排名和奖励。
6. 玩家当天未完成个人任务：连续天数归零。
7. 达到最高连续里程碑：当天发奖，存储天数回到零。
8. 午夜后没有新开局：不主动结算。
9. 后续首次 `/game/start`：`reconcile()` 追赶并完成结算。

## 8. 共同任务排名验收

构造不同人数和并列贡献：

- 共同目标未达成时无共同奖励；
- 只包含贡献大于 `0` 的玩家；
- 贡献降序，SteamID 升序作为确定性次序；
- 前 10% 和随后 30% 席位向上取整；
- 档位边界并列进入较高档；
- 至少一名有效贡献玩家进入最高档；
- 奖励分别为 100、90、80 赛季积分；
- 冻结排名写入后，奖励阶段不重新计算。

## 9. 奖励事务验收

对个人、共同和连续奖励分别验证：

1. 首次结算创建奖励流水并增加赛季积分。
2. 重复结算不再次增加积分。
3. 流水创建失败时积分不增加。
4. 积分更新失败时流水不提交。
5. `source`、`dayId`、配置版本、assignment、档位或连续天数正确。
6. 奖励创建后状态为 `pending`。
7. `/game/start` 返回正确 `pointInfo`，状态变为 `notified`。
8. 打开奖励记录后状态变为 `viewed`。
9. 展示动作不再次增加赛季积分。
10. 个人即时奖励与玩家挑战状态、共同贡献、比赛 ledger 同事务；模拟奖励写入失败时全部每日挑战写入回滚。
11. 比赛 ledger 保存 `personalRewardLedgerId`；相同 `/game/end` 重试返回同一 `seasonPoint/dayId/assignmentId`，但玩家积分只增加一次。
12. 对旧版缺少 `personalRewardLedgerId`、但带个人奖励快照的 ledger，只执行一次幂等兼容补偿。

同时核对玩家账户的真实赛季积分增量，不以响应中的数字代替数据库验证。

## 10. 游戏联调

后端通过后，再在配套 `windy10v10ai/game` 功能 PR 中执行 `docs/daily-challenge/gameplay-verification.md`。联调必须证明：

- 正确 addon 和正确功能 worktree；
- `/api/game/start` 返回 2xx 且包含 `matchStartedAt` 和玩家挑战快照；
- 10 分钟接取窗口使用同一比赛时间锚点；
- 5 分钟暂存同步不写正式进度；
- `/api/game/end` 返回 2xx；
- `/api/game/end.dailyChallenges` 在结算后包含最新正式进度、下一轮候选或三轮完成态；
- 游戏端拒绝同日旧 `updatedAt` 和旧挑战日快照，且相同时间戳的当前局临时进度仍可更新；
- 正常结算后 Firestore 正式进度增加；
- 逃跑或无效结算时暂存贡献未落库；
- 日终奖励进入真实赛季积分，并在下一次开局展示；
- 红点、数字角标、奖励记录和已查看状态与后端一致。

## 11. 验收记录格式

每次验收至少记录：

- 日期、分支、HEAD；
- 配置 ID、版本和哈希口径；
- Firestore 导入目录；
- API、代理和 addon；
- 测试账号；
- 执行命令与退出码；
- 通过项、失败项和未覆盖项；
- 数据库证据；
- 游戏内截图或日志证据；
- 最终结论：静态通过、后端集成通过、游戏内通过或未验证。

## 12. 快照 v2、三轮与星级定向验收

自动化测试必须覆盖：

- 旧配置缺少个人轮数、星级奖励、权重和倍率时使用兼容默认值；
- 任务级 `starTargets` 优先，未配置时按 0.75/1/1.5 倍率及单位规则取整；
- 三个候选独立、确定性抽取星级，允许同星；每轮结构始终为两种不同类别通用任务加一条英雄任务；
- 第 1/2 轮完成立即发奖并生成下一组，第 3 轮才设置 `completedAt`；
- 一/二/三星冻结奖励分别为 80/100/120，配置版本、目标和奖励不随后续发布变化；
- 免费刷新、付费刷新次数和 `refreshIndex` 跨轮累计，接取后禁止刷新；
- 相同 `/game/end` 重试不重复入账、不重复推进、不更换下一轮候选，并稳定回显同一笔个人奖励；
- 连续完成只认可三轮全部完成；
- `schemaVersion=1` 被拒绝，`schemaVersion=2` 被接受；比赛采集 `dataVersion` 仍为 2。
