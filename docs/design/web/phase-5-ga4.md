# 批次 5：网站接入 GA4

> 状态：已完成。长期设计见 [docs/web/README.md](../../web/README.md) 第 5 节「统计」，写代码时的规约见 [web/CLAUDE.md](../../../web/CLAUDE.md)「统计」。跟踪 issue #1122。

网站此前一个统计事件都没有：谁来了、从哪来、看了什么、有没有留下来，全是空白。服务端那套 Measurement Protocol 埋点只记录改数据的动作，补不出新用户与留存——那两个指标由 `first_visit` 事件推出来，MP 不会自动发，来源与推荐来源也只有浏览器知道。

## 决定

- **网页单独一条数据流，和游戏共用一个媒体资源**：共用才能靠 user_id 认出"游戏里的玩家"和"网站上的这个人"是同一个；分流是因为网页的自动事件与游戏侧自造的 `session_id` 混在一起，会话与互动时长没有一个能直接读。
- **用 gtag，不用 `firebase/analytics`**：Firebase 项目链接的媒体资源是 Ko-fi 站在用，`getAnalytics()` 会把事件静默发去那里。改链接要先确认 Ko-fi 站不依赖 Firebase Analytics，收益只是消掉这个地雷，本次不动。
- **登录后才设 user_id，退出时清掉**：不拿服务端那个 `player-uid` 提示 cookie 当初值，它可能已经过期，会把浏览记到别人名下。代价是每次会话的第一个 `page_view` 没有 user_id。
- **站内跳转的浏览量交给 GA4 增强型衡量**：Next 的路由跳转走 `history.pushState`，"基于浏览器历史事件的网页更改"默认开着就能计数，不自己监听路由。
- **`player_use_point` 补 `server_type` 参数**：路由挂没挂 `@AllowWeb()` 不代表来源——没有装饰器时官方服务器的 key 照样调得到，只有 guard 算出来的来源分得开网页与游戏。
- **加点补发 `player_use_point`**：此前只有洗点和觉醒发事件，加点是零数据。它花的是勇士等级不是积分，事件里的点数记的是加了几级，靠 `type` 区分；重发同等级是幂等成功，不记事件。

## 不做

- **不代理 gtag**：代理要把脚本与采集地址一起转回本站域名，还会把来源 IP 变成服务器、地理维度失真。大陆用户统计不到是已知代价，玩家分布以游戏侧的全量数据为准。
- **不发登录失败事件**：登录最容易失败的正是连不上 Google 的那批网络，事件同样发不出去，统计到的失败率必然偏低，排查仍然看生产日志。
- **不做 cookie 同意横幅**：个人项目、规模小，先不铺这套。
- **不给服务端事件传浏览器的 `_ga` 值**：那是为了让服务端事件并进网页会话，要每个相关接口多带两个参数，等浏览器侧确实发现漏报严重再说。

## 后续事项

- GA4 后台要手工做三件事，做完统计才真正开始：在游戏那个媒体资源下建网页数据流、把测量 ID 填进 `web/.env`、报表身份设成「混合」。
- 上线后在 DebugView 确认站内跳转有没有计 `page_view`，没有就去开增强型衡量的对应开关。
