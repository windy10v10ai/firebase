# 批次 13：网站签到

> 状态：已完成，对应 issue [#1214](https://github.com/windy10v10ai/firebase/issues/1214) 的第 1 项。身份卡上的签到见 [docs/web/README.md](../../web/README.md) 第 3 节。

Dota 2 7.41f 起本地主机上发不出任何 HTTP 请求，而几乎所有对局都跑在本地主机上。会员每日积分的发放挂在 `GET /game/start` 上，那个接口不再被调用，**每天 100 会员积分与补签实际上已经停发**。这一批把发放接到网站上。

## 决定

- **只做会员签到，接口形状为勇士积分预留**：勇士积分的数值要对标打一局的收益，还没定；响应按积分种类分组，届时只新增一个键、不改名
- **判定与写入只留一份，游戏与网站两个入口共用**：规则散成两份迟早对不上。游戏内那条不删——两个入口共用同一份签到状态，不会重复发放，官方服务器若恢复照样能签
- **服务方法拆成两个**，一个收已经取好的会员实体、一个自己去取：开局接口已经批量取过会员，让它走「自己去取」那条等于每局给每个人多读一次 Firestore
- **签到状态挂在 `PlayerInfoDto` 顶层，不挂在 `MemberDto` 下**：勇士积分签到面向所有玩家，挂在 member 下面非会员读不到自己的状态
- **加分与推进签到日不放事务，顺序固定为先加分后推进**：两个文档跨集合，fireorm 的事务只覆盖单个集合。中间失败时偏向多发，反过来是玩家白丢一天，多发没人投诉
- **领取明细用卡内嵌入块，不用浮层**：补签一次发 400，只把余额改掉玩家看不出这 400 从哪来；站上没有浮层组件，为一次反馈新做一套不值得
- **签到按钮用主按钮蓝，不用金色**：规范里金色的含义是「点了花会员积分」，签到是领取不是消费

## 不做

- **勇士积分签到**：数值待定，且要给非会员也发，需要新的签到日期字段
- **改签到数值与补签上限**：维持每天 100 会员积分、补签上限 7 天
- **改日切时区**：维持 UTC 零点（北京时间早 8 点刷新）。补签的天数计算全套基于 UTC，改了历史数据会错位一天

## 后续事项

- **勇士积分签到**另开批次：要在 `Player` 上新增签到日期字段（非会员也有 `Player` 文档），新建一个协调服务把两种积分串起来，controller 改一行
- **勇士积分是否补签**：按币种分组的结构允许它只有 `dailyPoint` 而没有补签字段，不必硬凑成同一个形状
- **加分与推进签到日的事务问题要在勇士积分批次重新评估**：那时单次发放的数值量级大得多，「偏向多发」的代价不再可忽略
