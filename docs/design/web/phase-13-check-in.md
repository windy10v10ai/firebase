# 批次 13：网站签到（后端）

对应 issue [#1214](https://github.com/windy10v10ai/firebase/issues/1214) 的第 1 项。本地主机策略的前一阶段见 [local-host/phase-1-backend.md](../local-host/phase-1-backend.md)。

## 背景

Dota 2 7.41f 起本地主机上 `CreateHTTPRequestScriptVM` 返回空，游戏内发不出任何 HTTP 请求，而几乎所有对局都跑在本地主机上。

后果不止 issue 里写的「勇士积分失去来源」。会员每日积分的发放同样挂在 `GET /game/start` 上，那个接口再也不会被调用，**会员每天 100 积分与补签实际上已经停发**。这一批先把会员签到接过来。

勇士积分签到（数值要对标打一局的收益）和两个页面的界面设计另开批次，本批只定后端数据流程，接口形状为勇士积分预留位置。

## 目标

1. 网站能触发会员签到，发放规则与游戏内完全一致
2. 前端能读到「今天签没签、能补几天」，用于渲染按钮状态
3. 接口与字段形状能容纳以后的勇士积分签到，届时只新增、不改名

## 不做

- **勇士积分签到**：数值待定，且要给所有玩家（含非会员）发放，需要新的签到日期字段
- **界面**：首页与个人主页的按钮位置、文案、反馈形式另行设计
- **签到数值与补签上限**：维持每天 100 会员积分、补签上限 7 天
- **日切时区**：维持 UTC 零点（北京时间早 8 点刷新）。补签的天数计算全套基于 UTC，改了历史数据会错位一天
- **删除 `GET /game/start` 里的签到**：两个入口共用同一份签到状态，不会重复发放；官方服务器若恢复，游戏内照样能签
- **Firestore 字段**：一个不加

## 数据流程

### 签到状态存在哪

判定只依赖 `Member` 文档上的三个字段：

| 字段 | 作用 |
|---|---|
| `lastDailyDate` | 上次签到日（UTC 日期） |
| `periodStartDate` | 本轮连续会员周期的起点。防止会员过期数月后重开时，把过期期间的漏签一次性补出来 |
| `expireDate` | 会员有效性，含 1 天宽限 |

规则由 `MembersService.getCheckInPoints()` 实现：今天未签发 100；中间漏签 N 天再补 N×100，补签上限 7 天，无需玩家操作；非会员或已过期全部为 0。

### 一次签到写两个文档

| 动作 | 集合 | 字段 |
|---|---|---|
| 加分 | `Player` | `memberPointTotal` |
| 推进签到日 | `Member` | `lastDailyDate` |

两者是不同集合里的文档，只是文档 id 都用 steamId。分开是因为生命周期不同：`Player` 记战绩与积分余额，人人都有、永久存在；`Member` 记会员到期日、等级与签到日，买了才有、过期作废，由支付宝 / 爱发电 / Ko-fi 的回调创建和续期。

签到同时碰这两个，是因为它读的是会员状态，发的是积分。

### 调用链

`GameService.addDailyMemberPoints` 里「算分 → 加分 → 推进签到日」这段提到 `MembersService.checkIn(steamId)`，成为单人版的签到动作。游戏与网站两个入口都调它，判定规则与写入只有一份。

`GameService` 那个批量方法保留，改为循环调用后把结果包装成游戏内弹窗要的 `PointInfoDto`——中英文案留在游戏那一侧，不进新接口，网站文案由 next-intl 出。

## 接口

`POST /player/:steamId/check-in`，放进 `PlayerInfoController`，无请求体。

- 挂 `@AllowWeb()`。guard 已经保证路由上的 `:steamId` 必须等于登录 uid，接口不自己做归属校验
- **不挂 `@AllowLocal()`**：游戏发不出请求，放开只是给泄露的本地 key 多一个冒用面

响应按积分种类分组，以后加勇士积分是新增一个 `seasonPoint` 键：

```ts
class CheckInResultDto {
  memberPoint: CheckInPoints; // { dailyPoint, catchUpDays, catchUpPoint }
  player: PlayerInfoDto;      // 刷新后的玩家信息，含 member
}
```

一并返回玩家信息，前端点完按钮一次请求就能把页面上的积分数字更新掉。

非会员或已过期调用返回 200，`memberPoint` 三个数字全为 0，不报错。

## 签到状态字段

`PlayerInfoDto` **顶层**新增，与响应体同形：

```ts
checkIn?: { memberPoint: CheckInPoints };
```

`dailyPoint` 为 0 即今天已签。前端一个类型两处用。

挂顶层而不是挂在 `MemberDto` 下面，是因为勇士积分签到面向所有玩家，挂在 member 下面会让非会员读不到自己的状态。代价是本批 `checkIn` 只在请求带 `include=member` 时才有值；勇士积分接上后它的状态在 `Player` 文档上，本来就每次都读，这个不一致届时自然消失。

取值由 assembler 调 `getCheckInPoints()` 算出。该方法是基于已读到的 member 实体的纯计算，不额外读 Firestore。

非会员的 `info` 响应本就没有 `member` 字段，因此拿不到签到状态，界面天然不显示按钮。

游戏客户端也读 `member`，本批只新增字段，不影响现有消费方。

## 已知取舍

**加分与推进签到日是两次独立写入，不放进事务。**两个文档跨集合，fireorm 的 `runTransaction` 只覆盖单个集合。

保持「先加分、后推进日期」的顺序：中间失败时偏向多发，反过来则偏向玩家白丢一天，多发没人投诉。代价是加分成功、推进日期失败时下次会重复发放 100 会员积分，概率取决于 Firestore 写入失败率，代价可忽略。

并发不是风险来源：重复发放要求两个请求卡进同一个约 100 毫秒的窗口，而前端点击后立即置灰按钮，客户端断开也不影响函数继续执行完。

**勇士积分批次要重新评估这条。**那时单次发放的数值量级大得多。

## 测试

单元测试（`MembersService.checkIn`）：

- 今日首次签到发 100
- 今日重复签到返回 0，不重复加分
- 漏签 3 天补 300
- 漏签超过 7 天只补 7 天
- 会员已过期不发放
- 处于 1 天宽限期内照常发放
- 会员过期后重新开通，不补过期期间的漏签

E2E：

- 网站 token 调用成功，积分与 `lastDailyDate` 都更新
- 路由 steamId 与登录 uid 不一致返回 403
- 未登录 401
- 本地 key 401

## 后续事项

- **勇士积分签到**：数值待定，需要在 `Player` 上新增签到日期字段（非会员也有 `Player` 文档），并新建一个协调服务把两种积分的签到串起来，controller 改一行
- **界面**：首页 `PlayerSummary` 与个人主页各放一个入口，共用一个组件。个人主页可以看别人的，别人的页面上不能出现签到按钮
- **勇士积分是否补签**：按币种分组的结构允许它只有 `dailyPoint` 而没有补签字段，不必硬凑成同一个形状
