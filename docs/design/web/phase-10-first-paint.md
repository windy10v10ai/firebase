# 批次 10：首屏与加载态

> 已完成，跟踪 issue：#1176。长期有效的设计见 [docs/web/README.md](../../web/README.md) 第 4 节「加载态」「屏幕档位」，写代码时的规约见 [web/CLAUDE.md](../../../web/CLAUDE.md)「加载态」「断点」。

## 一句话结论

**首屏由服务端读 `player-uid` 提示 cookie 决定渲染登录引导还是玩家内容；加载中直接渲染真实卡片布局，必有值的位置放骨架块、可能为空的只留位；全站断点统一为手机 / 平板 / 电脑三档。**

## 为什么首屏不知道用户是谁

登录凭据在 Firebase SDK 的 IndexedDB 里，不随请求发给服务器；客户端也要等 SDK 下载、初始化，并且每次启动都要联网校验一次用户（SDK 内部无条件执行），才给出结论。这个往返无法优化，只能绕开。不绕开时头部登录按钮判定完才插进来、整页下移，首页对已登录用户依次出现登录横幅 → 只有身份行的玩家卡 → 带数值的玩家卡三种高度。

把「不知道」拆成两类，各用各的手段：

| 不确定的是 | 手段 |
|---|---|
| **形状**：渲染登录横幅还是玩家卡 | 服务端读 cookie，首屏 SSR 就定 |
| **内容**：数值、将来的头像 | 容器定死尺寸，数据没到时放骨架块 |

## 登录态：`player-uid` 提示 cookie

- Firebase `onAuthStateChanged` 是唯一写入点：有用户写 uid，没有就删。登录、登出、token 失效、别的标签页登出都走这一处
- 非 HttpOnly、`max-age` 一年、`SameSite=Lax`。每次打开页面都会重写，活跃玩家等于永不过期；过期了也只是退回按未登录渲染，Firebase 随即校正
- **它不是凭据。** uid 本来就出现在地址里；API 只认 Firebase ID Token，伪造这个 cookie 只能骗过自己浏览器的第一帧

登录态因此只剩已登录 / 未登录两态。原先「加载中」兼管的「请求能不能发」下沉到 `apiFetch`：取 token 前等 SDK 就绪，否则 token 没恢复时发出去会拿到假 401。

登录链接的 origin 由根 layout 从请求头拼好传下去，登录按钮才能在服务端渲染。不用构建期环境变量：同一份生产构建同时从 `windy10v10ai.com` 和 App Hosting 默认域名访问，写死一个，另一个域名进来时 Steam 会拒绝回调。

## 加载态：一套 DOM

替换整页的占位组件自己一套布局，必须手工与真实页面保持同尺寸：原先的占位是单列两块大灰条，个人主页真实是两栏六张卡，数据到了整页一换照样跳。所以加载中直接渲染真实卡片，只把数值位置换成骨架块；骨架块用透明文字撑开，行高天然与真实文字一致。

- **属性卡加载中按未加点画出来**：进度条全空、数值与等级行放骨架块、按钮锁住。满级的卡数据到了换成同高的「已满级」一条，不跳
- **首页玩家卡的会员行始终占位**：非会员这一行本来就空，放骨架会预告不存在的内容，只留白。没选的两种：挪进数值网格（非会员要多看一行「未开通」）；非会员到达后收起（多数玩家不是会员，照样会跳）。个人主页会员卡的有效期行同理
- **首页身份行整行都是去个人主页的链接，窄屏右侧只留箭头**：375 宽下身份行去掉头像只剩约 250px，文字链接占掉 76px 后放不下 10 位 ID；缩小 ID 字号在 360 宽仍会折行
- 将来的 Steam 头像同理：固定尺寸的圆形容器，图片没到或加载失败时显示人形图标

## 字体：来不及就不换

网站字体 Noto Sans SC 按字形拆成上百个分片、不预加载，首屏先用系统字体画，下载完再换。系统字体字形更宽，换的一瞬间整页文字缩一下。`next/font` 的 `display` 用 `optional`：约 0.1 秒内没到就本次沿用系统字体，缓存后的访问直接用 Noto Sans SC。

代价是首次访问看到系统字体；某页含有未缓存分片的字时，同一页里可能混用两种字体。

## 断点：手机、平板、电脑三档

原先混用 `sm:`（640）、`md:`、`lg:` 且含义不统一，640 这个切换点也不在验证宽度里。实测英文已登录、10 位 ID 在 768 时，横排导航与 ID 文字同时挤进头部只剩约 12px，处在溢出临界。于是定为三档，平板按触控设备对待，账号 ID 文字、较矮的按钮到电脑档才出现（档位表见 [docs/web/README.md](../../web/README.md)「屏幕档位」）。

**卡片网格按三档定列数：手机 1 列、平板 2 列、电脑 3 列。** 属性页原为 1280 起三列，1024–1279 单卡被拉到 490–618px，与「单卡宽度保持在手机单列附近」的初衷相反；改到 1024 起三列后，各宽度单卡落在 323–489px，1024 下最长的按钮文字「Not enough points」也不溢出。

**属性卡的「满级」标签放在右侧数值上方。** 跟在名称后面时，英文长名称加标签在 375 手机上就会把标签挤到第二行，同一排卡片的进度条随之错位。没选的两种：放进等级那一行，英文会把等级说明撑成两行；去掉标签，扫一眼卡片顶部认不出哪些已满级。

## 不做

- **API 数据缓存**。HTTP `Cache-Control` 与「加点后立刻看到新值」冲突；应用层 stale-while-revalidate 有价值但不急，另见 #1175
- **服务端会话（HttpOnly session cookie + Admin SDK）**。服务端不碰用户数据，只需知道渲染哪套形状，一个 uid 足够
- **Firebase 自带的 `browserCookiePersistence`**。它把真凭据写进 cookie，需要配套代理路由并每秒轮询，为「服务端代表用户取数据」设计，这里用不上
- **路由级 `loading.tsx`**。跳转时显示整页 fallback，等于第二套布局
