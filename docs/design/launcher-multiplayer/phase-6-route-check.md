# 启动器联机 阶段 6：加入后实测选线与显示线路质量

> 状态：已完成，随启动器 0.5.4 发布，对应 #1425。长期说明见 [启动器联机](../../../launcher/README.md#联机)，`route_checked` 事件见 [docs/api/README.md](../../api/README.md) 的 `launcher_room_events` 字段。

加入时按「局域网 > 打洞 > 中转」取第一条连通的路，打洞能通就一直走打洞，哪怕整局都在丢包；玩家也看不到自己走哪条路。线上数据显示：直连丢包集中在约 14% 的加入，这些加入开局就差、整局都差，集中在晚高峰，换成中转多数能解决。

## 决定

- **连通后在直连和中转上同时测 10 秒，选定后整局不换**：差的线路开局就差，一次测准就覆盖大部分情况；中途换线收益小，还要一直维护两条路
- **只因丢包换，不因延迟换**：直连比中转只快约 30 ms
- **判断在启动器里，阈值由 API 随加入下发**：调阈值只部署 API，不下发就不测
- **由加入者决定，房主跟随**：旧版房主也能配合，不改隧道协议版本
- **只在 API 排第一的那台中转上比**：中转丢包多半是房主自己的线路，换哪台都没用
- **玩家看到「直连 / 中转 / 局域网」加延迟与丢包**：「中转」与「直连」对仗，单写「服务器」会和「服务器主机」混淆

## 不做

- 游戏中途持续比较、自动换线：开局好、中途变差的只占少数
- 加入前多测几秒：加入后测同样准
- 在几台中转之间实测挑选
- API 判断运营商：实测已能覆盖，不用维护 IP 库

## 后续事项

- 10-17 用两台中转一周的数据复查：加入前测到的中转丢包若能预示游戏中的丢包，再在 API 的排序里把丢包算进去
- 对照同一加入者之后的 `connection_quality`，看 10 秒的结果能不能代表整局；不少人前 10 秒正常、之后一直丢包时，再考虑中途换线
