# 启动器内嵌网站：网页访问与 Steam 登录

> 状态：设计方向已确认，尚未实现。长期设计见 [启动器内嵌网站](../../launcher/web-browser.md)。关联背景：[香港代理入口草稿 #1594](https://github.com/windy10v10ai/firebase/issues/1594)，该 issue 的新域名方案与本设计不是同一上线范围。

## 背景与目标

玩家即使能打开本站，也可能在跳转 Steam 登录时需要另开加速器。启动器承载现有网页并按需提供加速，让玩家在同一窗口完成登录及加点、觉醒，海外玩家保留直连体验。

## 关键取舍

- **复用现有启动器与网站**：不另做独立 APP，也不为此增加域名；账号页面继续由网站维护。
- **只加速内嵌网页**：集中解决网页与登录问题，避免把启动器扩成系统加速器。
- **复用选路思路，分开协议与探测**：现有游戏中转已有节点管理基础，但 UDP 测速无法证明 HTTPS 和 Steam 登录能用。
- **API 下发网页代理列表**：节点调整不要求发布启动器；具体接口位置、字段与授权协议在实现时确定。
- **保持浏览器数据与登录出口稳定**：降低反复登录和切换出口带来的体验问题。

完整的选路、鉴权、缓存与代理安全边界以长期设计为准，不在本文件复制。

## 首版原型

先在 Windows 验证 WebView2 加载当前生产域名及开发环境，复用现有 Steam OpenID → Firebase 登录流程。先尝试在现有新加坡机器部署独立的网页代理服务；香港作为后续对比候选，不以原型为由直接购买资源或调整现有游戏流量。

原型需证明按域名分流能覆盖 Steam 登录的实际跳转和依赖，并且更换线路时仍使用同一份浏览器数据。若浏览器配置机制要求重建实例，要验证关闭旧实例、重新打开页面不会清空会话或重放用户操作。

## 验证边界

| 场景 | 需要观察的结果 |
|---|---|
| 本站与 Steam 均可直连 | 保持直连，不因代理略快而切换 |
| 本站可达、Steam 不可达 | 本站直连，登录所需请求走可用代理 |
| 本站也不可达 | 通过代理加载页面、资源、同源 API 与 Firebase 登录请求 |
| Steam 登录完整往返 | 官方页可操作，验证完成后回本站获得正确账号权限 |
| 重启、exe 移动与升级 | 浏览器数据保留，网站会话可恢复及续期 |
| 配置接口或代理故障 | 可解释失败、尝试备用或直连，不静默重复提交加点等操作 |
| 缓存清理、退出与账号切换 | 资源缓存与会话操作分开，不出现上一个账号的可操作状态 |
| 代理边界 | 非白名单、内网目标及未授权请求被拒绝，日志不含登录秘密 |

原型的成功标准包括真实浏览器登录和数据操作，HTTP 200、Ping 或 Steam API 可达不能单独作为验收结论。真实网络结果及截图记录在实现 PR 或 issue。

## 实现前待验证

- WebView2 Runtime 与 .NET 依赖的安装体验，以及对现有单文件发布、自更新的影响。
- Steam 依赖域名、弹窗与跳转行为，开发站与正式站的完整回调。
- 现有新加坡机器的带宽和负载余量；香港对比测试后再确定节点与预算。
- 代理协议、登录前授权、防滥用和停用节点时的缓存失效机制。
- Mac 的内嵌浏览器、分流与数据持久化能力，以及两平台正式上线顺序。
- 站外支付、下载和系统协议链接的打开方式，避免默认代理任意站点。

## 不做

好友列表、邀请加入、Steam 客户端与游戏流量加速不在本阶段。也不开发跨系统浏览器的登录共享，不迁移 GCP 上的 Next.js 或 Firebase，不采购服务器或注册域名。
