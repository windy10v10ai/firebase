# 第 1 阶段：战绩与积分记录写入 BigQuery

> 状态：代码已完成，生产数据集待建。长期规范见 [docs/api/README.md](../../api/README.md)「分析数据」，插件升级另见 [#1327](https://github.com/windy10v10ai/firebase/issues/1327)。

GA4 的字段数与长度有上限、存的是事件格式；Firestore 只有累计值与最近 50 场；插件同步的是文档快照。三者做跨局统计都要先转换。本阶段由 API 在结算与积分变动时直接写原始数据进 BigQuery，只负责存，统计与展示放到后续阶段。

## 决定

- **新建数据集 `game_data`，和 GA4 导出、插件同步分开**：谁写的数据一眼能看出来；与插件同在 `asia-northeast1`，方便联查
- **一个玩家一局一行，电脑也写**：跨局平均、英雄与物品分析都按行分组
- **按日期分区，战绩表按 `steam_id`、`difficulty`、`hero_name` 聚类**：最常见的筛选是某个玩家或电脑、难度、英雄
- **服务端生成 `game_id`，原始 `match_id` 照存**：启动器开局的 `match_id` 恒为 `"0"`
- **每行存原始报文**：游戏端加字段后，建列之前数据不丢
- **只在结算被接受后写入，不另做去重**：线上结算全走本地主机结算与代理结算，两条都有 5 分钟冷却
- **积分记录在玩家服务的积分写入方法里统一记**：所有入口都经过这里，不会漏
- **用旧版流式写入（`insertAll`）**：每天约 1.8 万行，写入费每月约 0.06 美元；没选 Storage Write API，接入复杂得多却省不下钱
- **写入失败只记日志，积分记录不作为对账依据**：充值核对的兜底仍是插件快照，插件不能撤
- **生产数据不设过期**：长期分析与积分核对要完整历史，一年约 13 GB，每月不到 1 美元
- **本地开发写 `game_data_dev`，分区保留 30 天**：Firebase 模拟器没有 BigQuery；没选社区模拟器，它忽略分区与聚类，JSON 列行为也和线上不一致

## 不做

- 不导入 GA4 的历史数据：看后续统计需求再定
- 不拼代理结算的整局：一条请求只有一个玩家，也没有电脑
- 不记直接改数据库的积分变动（账号迁移脚本、控制台手改）：由插件快照兜底
