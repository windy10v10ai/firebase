# 每日任务刷新机制设计

日期：2026-08-23
状态：待评审
前置：[每日挑战 Phase1 重新设计](phase1-redesign-spec.md)

## 1. 背景

Phase1 上线后玩家反馈：抽到助攻、治疗这类需要队友配合的任务时，单人玩家很难完成，而当前没有任何补救手段——付费刷新在 Phase1 被整个删除了（见 Phase1 spec 3.6）。

本设计给所有玩家一次免费刷新的机会，并顺带修掉候选生成器里一个已被验证的随机性缺陷。

任务池本身对单人玩家不友好是另一条线（近期已有 #1072 / #1074 / #1076 在调），本设计不覆盖。刷新是通用兜底，不是任务池问题的替代方案。

## 2. 玩法规则

| 项 | 规则 |
| --- | --- |
| 谁能刷 | 所有玩家，无会员差异 |
| 次数 | **每轮 1 次**，一天最多 3 次 |
| 粒度 | 整组 3 个候选全换，星级重新洗牌 |
| 生效时机 | 局内实时，刷完当场可打 |
| 次数重置 | 完成一轮时归零、跨天时归零 |
| 未用完 | 不累积到下一轮 |

**不做会员差异**：刷新是补偿机制，修的是"抽到不称心任务"这个体验缺口。把它卖给会员，等于让非会员觉得体验被故意做坏。

**每轮一次而非每日一次**：每轮都可能抽到不称心的任务，每日一次只解决三分之一的痛点，且玩家第 1 轮用掉后剩下两轮无解。

## 3. 数据模型

`PlayerDailyTask` 只加一个整数字段：

```ts
@Collection()
export class PlayerDailyTask {
  // ... 现有字段不变
  refreshCount: number = 0;   // 本轮已刷新次数
}
```

这个字段同时干两件事：**限次数**和**做随机输入**。候选仍然全部重算，Phase1「候选不落库」的不变式不动。

老文档没有这个字段，读出来补 0（`normalize()` 里加 `?? 0`），不需要数据迁移。

上限是模块级常量，与 `ROUNDS_PER_DAY` 同处 `config/tasks.ts`：

```ts
export const MAX_REFRESH_PER_ROUND = 1;
```

## 4. 随机 seed 重新设计

### 4.1 现状与缺陷

现有 seed 是 `${dayId}:${steamId}:${round}`，哈希是 FNV-1a 32 位。生成器在三处用 `hash(...) % n` 取索引，其中两处的 `n` 是 2：第三个候选选通用还是英雄（`% 2`），星级洗牌的第一步（`% 2`）。

**FNV-1a 的最低位不参与哈希。** 初始值 `0x811c9dc5` 最低位为 1，质数 `0x01000193` 是奇数，因此乘法不改变最低位——整个哈希的最低位恒等于「1 XOR 所有输入字节最低位的 XOR」，不跑哈希就能算出来。已用 5 万组输入验证，无一例外。

三个可证明的后果：

| 现象 | 实测（8 万玩家 × 3 轮） |
| --- | --- |
| 每个玩家每天的「第三张卡类型」模式 | 8 种可能**只出现 2 种**：`通用/英雄/通用` 与 `英雄/通用/英雄`，各 50% |
| 三轮全通用 / 三轮全英雄 | **从不发生** |
| seed 追加 `:0` / `:1` 后，刷新前后第三张卡的类型 | **100% 翻转**，3 万次测试无一例外 |

第三条是本设计必须修它的直接原因：不修就加刷新，等于给玩家一个「刷新必然把第三张卡在通用和英雄之间切换」的确定性规律，星级洗牌的第一步同样必然翻转。

### 4.2 修法

在 FNV-1a 之后接一段 MurmurHash3 的 fmix32 收尾混合：

```ts
private hash(value: string): number {
  let hash = 0x811c9dc5;
  for (let index = 0; index < value.length; index++) {
    hash ^= value.charCodeAt(index);
    hash = Math.imul(hash, 0x01000193);
  }
  hash ^= hash >>> 16;
  hash = Math.imul(hash, 0x85ebca6b);
  hash ^= hash >>> 13;
  hash = Math.imul(hash, 0xc2b2ae35);
  hash ^= hash >>> 16;
  return hash >>> 0;
}
```

3 次移位 + 2 次乘法，成本可忽略。实测对比：

| 指标 | 现状 | 加 fmix32 |
| --- | --- | --- |
| 三轮「第三张卡」模式覆盖 | 2/8 种 | 8/8 种，各 ~12.5% |
| 刷新前后类型翻转率 | 100% | 50.1% |
| 通用池加权索引 `%19` 卡方（df=18，临界 34.8） | 29.8 | 10.5 |
| 英雄池 `%307` 卡方（df=306，临界 374） | 346.6 | 342.1 |

不换整个哈希算法：FNV-1a 加收尾混合已经达标，换算法要付同样的抖动代价却没有额外收益。

### 4.3 seed 结构

```
${dayId}:${steamId}:${round}:${refreshCount}
```

`generateCandidates` 增加一个参数，位置与 seed 顺序对齐：

```ts
generateCandidates(
  dayId: string,
  steamId: number,
  round: number,
  refreshCount: number,
  completedTaskIds: string[],
): TaskCandidateDto[]
```

生成仍是纯函数，且仍只依赖已落库的状态（`dayId` / `steamId` / 完成列表 / 刷新计数），因此确定性重算依然成立。

### 4.4 明确不做：排除上一组候选

刷新时不把刚才那 3 个任务从池中剔除。

代价是实测 **5.35%** 的概率通用槽会刷回同一条任务（通用池只有 10 条），玩家会感觉「刷了个寂寞」。英雄池 300+ 条，重复概率可忽略。

不做的理由是保持简洁：排除需要在每次重算时都先回算上一组（`refreshCount - 1`）作为排除列表——不只是刷新那一刻，之后每次 `/game/start` 重算候选时也必须重复这一步，否则重算结果与刷新时返回的不一致。这会让生成器从单向纯函数变成需要自我递归的形态，为 5% 的边缘体验付出的结构代价过高。

若上线后玩家反馈集中在这一点，再单独评估。

## 5. API 契约

### 5.1 `POST /daily-task/refresh`

新建 `daily-task.controller.ts`，路由挂在 `DailyTaskModule` 上。该模块已被 `GameModule` 引入，路由会自动注册。这是 Phase1「零独立接口」原则的第一次例外——局内实时刷新必须有一个玩家可主动触发的入口。

**鉴权对齐 `/game/start`**：`@Public()` + 手动校验 `serverType !== UNKNOWN`。不走默认 `AuthGuard`——它只认正式服与测试服 key，本地主机的 LOCAL key 会被拒，而本地主机的玩家同样在做每日任务、同样能拿积分。

请求：

```ts
export class RefreshDailyTaskDto {
  @ApiProperty()
  @IsInt()
  @Min(1)
  steamId: number;

  /** 客户端持有的任务日，取自 /game/start 响应 */
  @ApiProperty()
  @IsString()
  @Matches(/^\d{8}$/)
  dayId: string;
}
```

响应：复用 `DailyTaskSnapshotDto`，客户端整体替换本地状态。

### 5.2 快照 DTO 新增字段

```ts
export class DailyTaskSnapshotDto {
  // ... 现有字段不变
  @ApiProperty()
  refreshRemaining: number;   // 本轮剩余刷新次数
}
```

返回**剩余次数**而不是已刷次数，让上限这个常量只存在于服务端——将来调成每轮 2 次，客户端一行都不用改。

```ts
completedTasks.length >= ROUNDS_PER_DAY ? 0 : MAX_REFRESH_PER_ROUND - refreshCount
```

三轮打满时为 0（没有候选可刷）。`/game/start` 一并下发，玩家开局就知道本轮还能不能刷。

## 6. 服务端逻辑

单文档事务，复用 `DailyTaskStore.transact`：

```
today = getUtcDayId()

读文档（不存在则按新玩家创建）
if (文档.dayId !== today):
    跨天重置（含 refreshCount 归零），写回
    返回新快照                              // 不消耗次数
if (请求.dayId !== today):
    返回当前快照                            // 客户端状态陈旧，不消耗次数
if (completedTasks.length >= ROUNDS_PER_DAY):
    返回当前快照                            // 三轮打满，无候选可刷，不消耗
if (refreshCount >= MAX_REFRESH_PER_ROUND):
    返回当前快照                            // 额度用尽，幂等返回
refreshCount += 1，写回
返回新快照
```

**幂等是白送的。** 每轮只有 1 次额度，第二次请求必然命中「额度用尽」分支，返回的还是同一组候选。客户端网络重试、玩家连点两下都不会多扣次数、不会拿到第三组。不需要 `requestId`、不需要去重表。

这条性质**依赖上限为 1**。若将来改成每轮多次，幂等必须重新设计。

计数归零的两处：

- `resetForNewDay()`：跨天重置时置 0
- `recordGameEnd()`：写入 `completedTasks` 时置 0（完成一轮 = 进入下一轮）

归零的理由不只是「新一轮该有新额度」：计数是 seed 的输入，不归零会让第 1 轮刷过的玩家与没刷过的玩家在第 2 轮拿到不同候选，额度与随机性纠缠在一起。

**服务端不做时机门控。** 不校验对局进行到哪一步，由客户端决定刷新按钮何时可见（与 Phase1 的信任模型一致：客户端可信，服务端在结算路径上是纯记录器）。

## 7. 错误处理

| 情况 | 行为 |
| --- | --- |
| `serverType === UNKNOWN` | 拒绝，`logger.warn` |
| 请求 `dayId` 与服务端当前日期不符 | 不消耗次数，返回最新快照 |
| 三轮已打满 | 不消耗次数，返回当前快照 |
| 额度用尽 | 不消耗次数，返回当前快照（幂等） |
| 事务失败 | 返回错误，失败后如何处理由客户端决定 |

刷新是独立接口，失败不像 `/game/start` 那样需要静默降级——服务端如实返回错误即可，客户端怎么呈现是客户端的事。

**不记录刷新日志、不加 GA4 参数。** 代价是刷新行为没有任何观测数据：`refreshCount` 每轮归零，事后无法从 Firestore 反推刷新量或刷新后完成率。若之后需要评估这个功能的效果，得先补埋点。

## 8. 测试策略

### E2E（`test/*.e2e-spec.ts`，各用例独立 steamId）

1. **确定性守卫（最关键）**：刷新拿到新候选 → 再调 `/game/start` → 必须拿到逐字段相同的那一组。这条守着整个「候选不落库」，挂了玩家会看到候选跳变
2. 重复刷新 → 第二次返回同一组候选，`refreshRemaining` 恒为 0
3. 完成一轮 → 计数归零 → 新一轮可再刷一次
4. 跨天 → 计数归零、`completedTasks` 清空
5. 三轮打满 → 刷新不消耗次数，`candidates` 为空

### Unit

- `generateCandidates`：`refreshCount` 为 0 与 1 产生不同候选组；同样输入产生相同结果
- **哈希回归守卫**：存在某个 steamId，其三轮的**第三张卡全部为通用类型**。改回旧哈希这条必挂——旧哈希下该模式概率恒为 0（见 4.1）。注意每轮必定保底 1 个英雄任务，这里守的是第三张卡的类型，不是整轮的构成
- `normalize()`：老文档缺 `refreshCount` 字段时读出 0
- `refreshRemaining` 的计算：三轮打满时为 0

## 9. 客户端需要同步的改动（game 仓库）

- 任务面板加刷新按钮，按 `refreshRemaining` 决定是否置灰
- 点击 → vscripts 发 `POST /daily-task/refresh` → 拿到快照整体替换本地状态
- 刷新按钮的可见时机、请求失败后如何处理，全部由客户端决定，服务端不做约束
- 三语文案：刷新按钮、剩余次数、失败提示

## 10. 上线顺序与影响

**API 先，game 后**，与 Phase1 spec 12.5 一致。新字段与新接口对老客户端完全无影响：老客户端不会调刷新接口，多出来的 `refreshRemaining` 会被忽略。

**一次性抖动**：seed 结构与哈希一起改，部署那一刻起，当天所有玩家**下一局**的候选会变一次。本局不受影响——`/game/end` 是纯记录器，不验证 taskId，玩家正在打的任务照常结算。想把影响面压到最小就在 UTC 日界附近部署。

## 11. 明确不做的事

| 项 | 理由 |
| --- | --- |
| 排除上一组候选 | 见 4.4，为 5% 的边缘体验付出的结构代价过高 |
| 会员额外次数 | 刷新是补偿机制，不作为付费点 |
| 服务端时机门控 | 与 Phase1 信任模型一致，交给客户端 |
| 刷新日志与 GA4 统计 | 保持简洁。代价见第 7 节：刷新行为没有观测数据 |
| 刷新次数累积 | 每轮独立额度，用不掉作废 |
| 按本局真人数量调整任务池 | 会破坏跨局候选稳定性——同一轮在不同人数的局里会算出不同候选 |
